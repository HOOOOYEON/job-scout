# 日报渲染结构

日报的目标是**让用户在一屏之内决定今天投哪几个**。所以顺序比内容重要。

## 固定结构

按下面七段顺序输出，不要调整：

### 第一段：今日概览

三五行的总览，让人先有全局感：

```
今日候选 26 个 → 入围 7 个
分线：AIGC 3 个 · 运营 2 个 · 产品 2 个
已确认双休 5 个 · 有待核实项 2 个
```

### 第二段：分线岗位卡

按方向分线，每条线内的岗位按综合分降序。

每张卡按 `card-spec.md` 的 10 个字段渲染，不要偷工减料。

线内排序规则：

1. 综合分降序
2. **双休待核实的排到该线末尾**，即使分数更高
3. 分数相同时，通勤时间短的排前面

### 第三段：双休已确认清单

把本次所有明确标着 `双休 ✅` 的岗位单独列一遍。

这一段的价值在于：用户如果今天只想做一件确定的事，就看这一段。

### 第四段：可直投邮箱清单

把所有查到公开 HR 邮箱的岗位列出来，格式：

```
公司名 · 岗位名 → hr@example.com
```

直投比走网申表单的到达率高得多，这一段是给「今天就想发几封邮件」的场景准备的。

如果按方向准备了不同的邮件正文，要在这里标注清楚哪封配哪个岗位。

### 第五段：待核实项汇总

把所有写着「待核实」的字段集中列出来，注明**用什么方式可以核实**：

```
- A 公司：双休未注明 → 可在面试初筛时直接问
- B 公司：社保基数存疑 → 员工评价提到按最低基数缴
- C 公司：邮箱待核实 → 建议走官网表单
```

集中列出来，用户才能一次性安排核实动作，不用来回翻卡片。

### 第六段：风险提示

需要特别注意的情况。没有就写「今日无明显风险」。

例如：某公司近期大量招同岗位、某岗位 JD 描述与实际职责可能不符。

### 第七段：筛除说明

写明今天淘汰了多少、按什么理由淘汰的。格式见 `hard-gates.md`。

这一段是**规则在起作用的证据**。没有它，用户无法判断「怎么今天只有 3 个岗位」。

## 排序与数量规则

- **名额是上限，不是任务量**。设定每天 5 个，实际只有 3 个达标，就给 3 个并说明原因。
- **不够数时如实说**，绝不拿低分岗位凑数。凑数会让用户对整份日报失去信任。
- **多条线之间不做分数比较**。不同方向的评分尺子不同，跨线比较没有意义。

## 交付方式

日报要落成文件，同时在对话正文里把**每条线的头部岗位**的核心信息讲一遍：

- 公司名、岗位名
- 邮箱
- 薪资
- 通勤
- 双休
- 社保
- 综合分

不能只丢一个文件链接。用户在手机上经常懒得点开文件，正文没内容等于日报没送到。

## 落盘命名

```
求职日报-YYYY-MM-DD.md
```

固定命名便于按日期回溯对比。
