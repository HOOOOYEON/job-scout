# 去重：为什么必须多表联查

**结论先行：判断一个岗位是否「已投」，必须同时查投递记录、推荐记录、岗位记录三个来源。
只查其中一两个，一定会漏。**

## 为什么单一来源会漏

岗位进入系统的路径不止一条，每条路径落在不同的记录里：

| 路径 | 落在哪 |
|---|---|
| 日报推荐后用户投了 | 推荐记录 + 投递记录 |
| 用户在别处看到岗位，回来登记已投 | **只有投递记录** |
| 岗位被采集但还没推荐过 | 只有岗位记录 |

关键在于第二种：**走「直接登记已投」这条路的岗位，从来没有进过推荐列表。**

如果去重时只查推荐记录和岗位记录，这些岗位在系统里看起来完全「不存在」，
于是会在几天后被当成新岗位重新推荐一次。

## 真实事故

这不是假设。曾经出现过这样一个情况：

某次日报执行时只查了推荐记录和岗位记录做去重，结果把三个**两天前已经通过邮件直投**
的岗位当成新岗位推了出去。这三个岗位走的是「登记已投」路径，在推荐记录里查无此岗。

后果不只是浪费用户时间 —— 同一家公司短期内收到两次同样内容的投递，是实打实的负面印象。

**事故根因**：去重查询的覆盖面不完整，漏掉了只存在于投递记录里的岗位。

## 正确做法

去重时必须**取三个来源的并集**：

```
已占用 = 投递记录 ∪ 推荐记录 ∪ 岗位记录
```

任何一个出现在这个并集里的岗位，**都不得进入「新推荐」位**。

如果出于信息完整性考虑仍要展示，必须明确标注历史状态，例如：

- 「已于 X 月 X 日投递」
- 「已于 X 月 X 日推荐过，本次为更新」

## 去重的匹配键

同一家公司的同一个岗位，在不同平台上的 URL 往往不一样，所以**不能只按 URL 去重**。

推荐用组合键：

```
去重键 = 规范化公司名 + 规范化岗位名 + 城市
```

规范化时要做这些处理：

- 去掉公司名里的「有限公司」「股份有限公司」等后缀
- 去掉岗位名里的「急聘」「高薪」「双休」等营销词
- 统一全角/半角、繁简体
- 岗位名里的「专员 / 助理」这类差异要人工确认，不要当成同一个

URL 作为辅助校验：URL 相同的一定是重复，URL 不同的未必不是重复。

## 执行顺序

1. 拉取三个来源的完整记录
2. 对每条记录生成规范化去重键
3. 汇总成已占用集合
4. 对每个新候选计算去重键，在集合里查
5. 命中 → 移出「新推荐」，按历史状态归类
6. 未命中 → 进入硬门槛过滤

这一步要在硬门槛之前做 —— 先排除已投的，能省掉大量无用的字段核实工作。

## 自检

交付日报前问自己一句：**「我今天推荐的岗位里，有没有可能有一个其实早就投过了？」**

如果回答这个问题需要犹豫，说明去重没做全，回去重查。
